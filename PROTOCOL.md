# Protocol reference and implementation

Read reference `internal/auth/auth.go`, `internal/upstream/client.go`, `headers.go`, `payload.go`, `sanitize.go`, and full `sse.go` in workbuddy2api e4d5d3a. Source login.sh references a missing cmd/login; its README is insufficient to reproduce login. Inspected official CodeBuddy npm 2.187.0 `dist/codebuddy.js` ExternalLinkAuthenticationProvider and AccountScopedExternalLinkAuthenticationProvider to recover token polling/account endpoints and pending codes. No upstream fingerprint sanitization is applied: message content is preserved.

CN chat/auth base `https://copilot.tencent.com`; global base `https://www.workbuddy.ai`. Origin/referer CN `https://www.codebuddy.cn`, global `https://www.workbuddy.ai`; UA `CLI/2.63.2 CodeBuddy/2.63.2`.

- POST `/v2/plugin/auth/state?platform=workbuddy` JSON `{}` -> envelope data `{state,authUrl}`. Platform is a QUERY parameter: a JSON-body-only platform returns code 10001 `platform is empty`. Confirmed live.
- GET `/v2/plugin/auth/token?state=...` -> envelope token fields. Code 11217 means authorization pending; confirmed live from both Linux HTTPS and actual Android app. State is generated remotely and encrypted locally. No PKCE scheme is invented.
- GET `/v2/plugin/accounts` with access token and domain -> data.accounts; prefer pluginEnabled + lastLogin. Resolved from official external-link flow. Login completion requires both token and account retrieval.
- POST `/v2/plugin/auth/token/refresh`: only this request sends `X-Refresh-Token`, plus `X-Auth-Refresh-Source: workbuddy`, optional enterprise ID. Refreshes are serialized, persistent atomically, and performed 5 min before expiry or once after upstream 401. No auth headers or upstream bodies in logs. Official CLI timestamps in milliseconds are normalized to seconds when importing.
- GET `/console/enterprises/personal/models`: select models referenced by agents[name=cli], skip disabled/missing IDs, preserve maxInputTokens/maxOutputTokens and reasoning.supportedEfforts. Also pass through known upstream rate fields (`multiplier`, `rate`, `倍率`, `inputMultiplier`, `outputMultiplier`) when present; no local multiplier is invented when absent. Cache TTL 5 min; explicit UI update available. Refresh failure does not invent fallback model IDs.
- POST `/v2/billing/meter/daily-checkin`: CN billing endpoint with `{}` and account billing headers. The Android UI exposes an immediate check-in action; business messages such as “今日已签到” are treated as an idempotent result.
- POST `/v2/billing/meter/get-user-resource`: query active `p_tcaca` resources and aggregate `CycleCapacityRemain` (falling back to the compatible capacity fields) for the displayed available points.
- POST `/v2/chat/completions`: always stream=true. Preserve OpenAI messages/tools. tool_choice object -> string, named function -> function name; none removes tool definitions and choice. reasoning effort is clamped only when cached model supported efforts are known. No refresh token on chat headers. Chat user/enterprise/domain headers use reference X-No-* fallbacks, X-Product=SaaS.
- SSE reader supports CRLF, fragmented transport via BufferedReader, multiline data and final unterminated event. Normalize empty/noise fields; preserve reasoning, tool deltas, usage, finish reason. Streaming flushes each event; non-streaming merges tool calls by index and argument fragments in sorted order, strips streaming tool index, returns chat.completion. Premature EOF without a finish_reason yields explicit incomplete_stream; stream errors propagate as SSE error + DONE. Upstream cancellation uses connection close/read timeout; disconnecting local client is detected on the next downstream write. Upstream EOF after a finish_reason is accepted even without DONE.

Local endpoints: GET /health or /healthz (public liveness, authenticated boolean), GET /v1/models, GET /v1/status or /status, POST /v1/chat/completions (API key required). /healthz is liveness, not upstream readiness. Unknown endpoints including /v1/responses are 404. CORS supports OpenAI browser clients. HTTP supports Content-Length, chunked and gzip bodies; bounded 8 MiB decoded requests and 32 MiB aggregate responses, bounded thread queue, 4 simultaneous chats, no request-body persistence.
